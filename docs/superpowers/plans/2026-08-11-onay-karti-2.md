# Onay Kartı 2.0 — Bilgilendirici Karar Kartı Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the approval card from *"Ajan X, Y eylemini yapmak istiyor: onayla/reddet"* into a card that produces an **informed** decision — carrying the requesting authority, the trust signals the policy already computed, the concrete operand, and whether the action is reversible — plus a typed rejection whose reason reaches the model, and a hash-chained decision ledger the agent cannot rewrite.

**Architecture:** Everything here already exists somewhere in the system and is thrown away at a boundary. `policy.write_audit` computes `actor`, `zone`, `trust_level`, `tier` and the decision cause (`brain/app/policy.py:59-97`) and writes them to `audit_log`; `approvals.request` never receives them (`brain/app/approvals.py:200-256`), so `_project` cannot return them (`approvals.py:140-158`), so `ApprovalDto` cannot carry them (`android/.../data/net/ApprovalApi.kt:52-69`), so the card cannot show them (`android/.../ui/chat/ApprovalCard.kt:58-122`). This plan widens that one pipe end to end and adds two things that do not exist at all: a per-tool reversibility fact, and an append-only decision ledger.

**Tech Stack:** Python 3.12 / FastAPI / Firestore (brain); Kotlin / Compose / Retrofit 3 (Android, compileSdk 36); pytest; JUnit.

**Interfaces:**

- Produces: `config.TOOL_REVERSIBILITY: dict[str, bool]` and `config.is_reversible(tool_name: str) -> bool`. **Unknown tool → `False` (irreversible)** — the fail-closed direction, because treating a destructive unknown as reversible is exactly the mistake that makes a timeout silently permissive later (Task 4 branches on this).

## Task 4: Expiry by reversibility + hash-chained decision ledger

**Files:**
- Modify: `brain/app/approvals.py` (`decide()` expiry branch ~365-376, `expire_due()` ~431-453)
- Create: `brain/app/decision_log.py`
- Test: `brain/tests/test_decision_log.py` (create), `brain/tests/test_approvals.py`

**Interfaces:**
- Consumes: `reversible` from Task 2, `reason` from Task 3.
- Produces:
  - `decision_log.append(db, *, approval_id, user_id, decision, by, at, actor, zone, cause, operand, reversible, reason) -> str` — writes one document to the `decision_log` collection containing `prev_hash` (the hash of the previous entry for this user, `""` for the first) and `hash` (sha256 over the canonical serialization of this entry's fields **including `prev_hash`**). Returns the new hash.
  - `decision_log.verify(db, user_id) -> tuple[bool, str | None]` — walks the chain oldest-first and returns `(True, None)` or `(False, "<id of the first broken link>")`.
  - Expiry semantics split by reversibility (§5.6): an **irreversible** approval that times out becomes `expired` and is treated as a denial exactly as today (fail-closed, unchanged); a **reversible** one also becomes `expired` but records `outcome=EXPIRED_NOTIFY_OUTCOME` and emits a notification hook so the agent can learn the request lapsed rather than reading it as a hard "no".

**Why the hash chain and not a signature:** P5 — with a single user, signing buys little; a chain makes retroactive edits detectable for the cost of one hash per decision. `verify()` is what turns that into evidence.

**Honest limit to write in the module docstring:** the chain proves *tampering*, not *authorship*; anything that can write to Firestore can also rewrite the whole chain from a given point forward. Making the collection agent-unwritable is a Firestore rules change (K3) and is NOT part of this task — name it in the docstring as the remaining half.

## Out of scope, and why

- **Kademeli izin merdiveni (bir kez / bu oturum / her zaman)** — its own slice; it changes what the policy allows without asking, which is the one direction that can silently widen authority.
- **Firestore rules making `decision_log` agent-unwritable** — the other half of K3; a rules/IAM change, not application code, and it deserves to be verified against the live project rather than asserted in a test.
- **Taint bayrağı (P4)** — the highest-security-return item in the analysis, but independent of the card; next slice.
- **Politikayı YAML'a taşıma (§5.10 A)** — worth doing when the rule count justifies it; the analysis itself says the payoff arrives past ~30 rules.
